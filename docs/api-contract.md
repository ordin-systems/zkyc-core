# v0.3.1 Full-Stack API Contract

## Transport rules

Request bodies accept only `application/json` or `application/*+json`. Unsupported media types return `415 UNSUPPORTED_MEDIA_TYPE`. Unknown/missing fields, malformed JSON, mixed direct/delegated bindings, and prototype-control fields return `400 INVALID_REQUEST`. Responses use `cache-control: no-store`.

Nested own `__proto__` keys inside `actionContext` remain canonical data and cannot alter object prototypes.

A transport-required artifact field may still contain a structurally malformed or unregistered artifact. `/evaluations` reports those authority failures as exact HTTP `200` reason-coded denial variants rather than inventing trusted bindings.

| Method | Route | Purpose |
|---|---|---|
| `GET` | `/health` | Local service/version/state signal |
| `POST` | `/credentials` | Issue registered scoped credential v2 |
| `POST` | `/credentials/:credentialId/revoke` | Revoke registered credential |
| `POST` | `/delegations` | Issue registered one-hop attenuated delegation |
| `POST` | `/delegations/:delegationId/revoke` | Revoke registered delegation |
| `POST` | `/evaluations` | Evaluate exact direct/delegated authority; optionally issue `ALLOW` receipt v2 |
| `POST` | `/step-up/requests` | Create request v2 from retained `decisionLogId` |
| `POST` | `/step-up/requests/:requestId/resolve` | Approve/reject using exact-scope human credential |
| `POST` | `/step-up/authorizations/consume` | Verify complete step-up v2 binding and consume once |
| `POST` | `/receipts/consume` | Verify complete receipt v2 binding/current authority and consume once |
| `GET` | `/zkya/onboarding-views/:decisionLogId` | Return retained current-state onboarding projection |
| `GET` | `/decision-log` | Return defensive-copy reason-coded entries |

## Direct and delegated evaluation requests

Common required fields are `authorityMode`, `principal`, `action`, `resourceId`, `actionContext`, `policy`, and `issueReceipt`.

- `DIRECT` additionally requires `credential` and rejects delegated fields.
- `DELEGATED` requires `delegateIdentityCredential`, `grantorCredential`, and `delegation` and rejects direct `credential`.

`receiptExpiresAt` is required only when `issueReceipt` is true. A receipt is returned only for the exact fully authority-bound `ALLOW / POLICY_ALLOW` generated by that request. Every negative, unbound, or partially bound result is receipt-free. There is no arbitrary signing route.

## Exact decision binding variants

All normal decisions include common v2 fields: outcome, reason, mode, typed subject, action/sensitivity, resource, context hash, exact policy, and decision time. Additional authority fields follow the binding stage actually trusted by core:

| Variant | Exact authority binding |
|---|---|
| Unbound direct denial | `DIRECT`, `DENY`, and `CREDENTIAL_MISSING`, `CREDENTIAL_MALFORMED`, or `CREDENTIAL_UNKNOWN`; no acting credential, effective scope, direct credential ID, delegated fields, metadata, approver capability, or receipt |
| Bound direct decision | Acting credential and effective scope; `credentialId` equals `actingCredentialId`; no delegated fields |
| Unbound delegated denial | `DELEGATED`, `DENY`, and delegate-identity `CREDENTIAL_MISSING`, `CREDENTIAL_MALFORMED`, or `CREDENTIAL_UNKNOWN`; the SDK also permits coarse server-authoritative `DELEGATION_GRANTOR_CREDENTIAL_INVALID` unbound with no independent proof of private state; no acting/direct/delegated bindings, metadata, approver capability, or receipt |
| Acting-only delegated denial | Trusted delegate identity credential and effective scope; no direct `credentialId`, grantor/delegation fields, approver capability, or receipt |
| Fully bound delegated decision | Trusted delegate credential/effective scope plus exact grantor, grantor credential, delegation ID, and delegation binding hash; no direct `credentialId` |

Outcome correlation is exact: `ALLOW` requires `POLICY_ALLOW`; `STEP_UP` requires `HUMAN_APPROVAL_REQUIRED` and the exact approver capability; `DENY` forbids both success codes and forbids an approver capability.

Metadata never grants authority. It is omitted for unbound decisions and may appear only when copied from a structurally trusted acting credential.

## Correlation and authority boundary

The SDK validates exact response shape and rejects contradictions in request-observable facts: mode, principal ID/type/affiliations, action, resource, context hash, policy ID/version/effect, supplied artifact hashes, time windows, scope, delegation identities, and attenuation.

Private registration and revocation remain server-authoritative. Correctly shaped denial-only results such as `CREDENTIAL_UNKNOWN`, `CREDENTIAL_REVOKED`, `DELEGATION_UNKNOWN`, and `DELEGATION_REVOKED` do not claim independent SDK proof of private state and never widen authority.

`DELEGATION_GRANTOR_CREDENTIAL_INVALID` deliberately has a coarse unbound SDK form for server-authoritative cross-authority/core contexts. The public Hono evaluation path normally emits its fully bound form after retaining validated authority artifacts. Neither shape proves private registration or revocation to the browser.

## Delegation issuance and dual transport

`POST /delegations` requires grantor principal/credential, delegate principal, policy, capabilities, allowed actions/resources, and expiry. The adapter injects ID and issue time. Core issuance requires an active exact root grantor credential, subset attenuation, exact policy binding, expiry no later than the grantor credential, and no delegated `delegation:issue` capability.

`DELEGATION_IDENTITIES_NOT_DISTINCT` has two deliberate transports:

| Operation | HTTP/result | Contract |
|---|---|---|
| `POST /delegations` issuance | HTTP `400` | Exact domain-error envelope `{error:{code:"DELEGATION_IDENTITIES_NOT_DISTINCT",message:"delegation request is invalid"}}`; no delegation issued |
| `POST /evaluations` delegated evaluation | HTTP `200` | `{logId,decision}` with acting-only delegated `DENY / DELEGATION_IDENTITIES_NOT_DISTINCT`; no direct credential ID, grantor/delegation fields, or receipt |

The evaluation response is never “repaired” by echoing untrusted grantor or delegation identifiers.

## Step-up provenance and scope

`POST /step-up/requests` accepts only a retained `decisionLogId` and expiry. The adapter retrieves the retained `STEP_UP / HUMAN_APPROVAL_REQUIRED` decision. Resolution requires `resolution`, a `HUMAN` approver, and matching active approver credential with the required capability, `step-up:resolve` action, and original resource.

Authorization consumption requires the complete request/subject/type/acting-credential/effective-scope/action/resource/context/policy/approver binding and mode-specific direct credential or delegated grantor/delegation binding.

## Receipt v2 expected binding

Every common expected field is required before nonce consumption: authority mode, typed subject, acting credential, effective scope, action/sensitivity, resource, context hash, policy, decision/reason, and approver capability when applicable. Direct mode additionally requires `credentialId`; delegated mode requires the full grantor/delegation binding. Nonce and timestamps are signed/time-validated rather than caller-selected expected bindings.

## Retained onboarding projection

`OnboardingView.version` remains `1`. Its receipt projection is exact:

```ts
{
  consumptionStatus: "NOT_ISSUED" | "UNCONSUMED" | "CONSUMED";
  lastAttempt:
    | { outcome: "NONE" }
    | { outcome: "ACCEPTED"; reasonCode: "RECEIPT_VALID" }
    | { outcome: "REJECTED"; reasonCode: AssociatedReceiptFailure };
}
```

Legal reachable pairs are:

| Durable status | Latest attempt |
|---|---|
| `NOT_ISSUED` | `NONE` |
| `UNCONSUMED` | `NONE` or associated `REJECTED` |
| `CONSUMED` | `ACCEPTED / RECEIPT_VALID` or associated `REJECTED` |

Consumption is monotonic: only `UNCONSUMED → CONSUMED`. Replay projects `CONSUMED + REJECTED / RECEIPT_REPLAYED`. Malformed input and attempts not associated with a retained signature hash leave both axes unchanged; `RECEIPT_MALFORMED` is therefore a consume response but not a retained associated rejection reason. Legacy single-status shapes and impossible pairs are rejected.

## Error and authority results

Transport/input and issuance-domain errors use the exact envelope:

```json
{
  "error": {
    "code": "INVALID_REQUEST",
    "message": "request body is invalid"
  }
}
```

Reason-coded `ALLOW`, `DENY`, `STEP_UP`, approval/rejection/expiry, replay, and binding mismatch are authority results rather than unhandled exceptions. Unexpected failures return a generic fail-closed response without internals.

## Boundary

The API has no authentication, tenancy, rate limiting, durable state, or protected-action route. It is loopback reference evidence and must not be deployed as-is.
