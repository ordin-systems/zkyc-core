# v0.3 Full-Stack API Contract

## Transport rules

Request bodies accept only `application/json` or `application/*+json`. Unsupported media types return `415 UNSUPPORTED_MEDIA_TYPE`. Unknown/missing fields, malformed JSON, mixed direct/delegated bindings, and prototype-control fields return `400 INVALID_REQUEST`. Responses use `cache-control: no-store`.

Nested own `__proto__` keys inside `actionContext` remain canonical data and cannot alter object prototypes.

## Routes

| Method | Route | Purpose |
|---|---|---|
| `GET` | `/health` | Local service/version/state signal |
| `POST` | `/credentials` | Issue registered scoped credential v2 |
| `POST` | `/credentials/:credentialId/revoke` | Revoke registered credential |
| `POST` | `/delegations` | Issue registered one-hop attenuated delegation |
| `POST` | `/delegations/:delegationId/revoke` | Revoke registered delegation |
| `POST` | `/evaluations` | Evaluate exact direct/delegated authority; optionally issue `ALLOW` receipt v2 |
| `POST` | `/step-up/requests` | Create request v2 from retained `decisionLogId` |
| `POST` | `/step-up/requests/:requestId/resolve` | Approve/reject using exact-scope human credential |
| `POST` | `/step-up/authorizations/consume` | Verify complete step-up v2 binding and consume once |
| `POST` | `/receipts/consume` | Verify complete receipt v2 binding/current authority and consume once |
| `GET` | `/zkya/onboarding-views/:decisionLogId` | Return retained current-state onboarding projection |
| `GET` | `/decision-log` | Return defensive-copy reason-coded entries |

## Direct and delegated evaluation

Common required fields are `authorityMode`, `principal`, `action`, `resourceId`, `actionContext`, `policy`, and `issueReceipt`.

- `DIRECT` additionally requires `credential` and rejects delegated fields.
- `DELEGATED` requires `delegateIdentityCredential`, `grantorCredential`, and `delegation` and rejects direct `credential`.

`receiptExpiresAt` is required only when `issueReceipt` is true. A receipt is returned only for the exact `ALLOW / POLICY_ALLOW` generated by that request. There is no arbitrary signing route.

## Delegation issuance

`POST /delegations` requires grantor principal/credential, delegate principal, policy, capabilities, allowed actions/resources, and expiry. The adapter injects ID and issue time. Core issuance requires an active exact root grantor credential, subset attenuation, exact policy binding, expiry no later than the grantor credential, and no delegated `delegation:issue` capability.

## Step-up provenance and scope

`POST /step-up/requests` accepts only:

```json
{
  "decisionLogId": "decision-log:example",
  "expiresAt": "2026-08-09T05:00:00.000Z"
}
```

The adapter retrieves the retained `STEP_UP / HUMAN_APPROVAL_REQUIRED` decision. Resolution requires `resolution`, a `HUMAN` approver, and matching active approver credential with the required capability, `step-up:resolve` action, and original resource.

Authorization consumption requires the complete request/subject/type/acting-credential/effective-scope/action/resource/context/policy/approver binding and mode-specific direct credential or delegated grantor/delegation binding.

## Receipt v2 expected binding

Every common expected field is required before nonce consumption:

- `authorityMode`;
- `subjectId`, `subjectType`, `actingCredentialId`, `effectiveScopeHash`;
- `action`, `actionSensitivity`, `resourceId`, `contextHash`;
- `policyId`, `policyVersion`, `decision`, `reasonCode`;
- `requiredApproverCapability` when applicable.

Direct mode additionally requires `credentialId`. Delegated mode requires `grantorId`, `grantorType`, `grantorCredentialId`, `delegationId`, and `delegationBindingHash`. Nonce/timestamps are signed/time-validated rather than caller-selected expected bindings.

## Retained onboarding view

The version 1 reference projection includes principal, mode, delegated scope or `null`, current verification status, exact eligible action/resource with status/reason, approval state, receipt state, and policy ID/version. It rechecks retained authority at read time. It is not durable state or a credential.

## Error and authority results

Transport/input errors use an exact envelope:

```json
{
  "error": {
    "code": "INVALID_REQUEST",
    "message": "request body is invalid"
  }
}
```

Reason-coded `ALLOW`, `DENY`, `STEP_UP`, approval/rejection/expiry, replay, and binding mismatch are authority results rather than unhandled exceptions. Unexpected failures return a generic fail-closed response without internals.

## Boundary

The API has no authentication, tenancy, rate limiting, durable state, or protected-action route. It is loopback reference evidence and must not be deployed as-is.
